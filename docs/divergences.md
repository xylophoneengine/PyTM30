# Divergences and conformance notes

Where ANSI/IES TM-30-20 and existing implementations differ, PyTM30 follows
the standard. Each item below cites the governing clause.

## Why these two comparison points

[luxpy](https://github.com/ksmet1977/luxpy) and
[colour-science](https://github.com/colour-science/colour) are the two
established Python implementations of TM-30 and served as accuracy
references during PyTM30's development (colour-science remains the
cross-validation reference; see the fixture section at the end).
Documenting where PyTM30's output differs from theirs -- and which clause
drives each difference -- is what lets a user reconcile numbers across
implementations instead of guessing which one drifted.

Versions and environment referenced throughout:

- "luxpy" = [luxpy](https://github.com/ksmet1977/luxpy) v1.12.5
- "colour-science" = [colour-science](https://github.com/colour-science/colour) 0.4.7
- Verification environment: Python 3.12.13, numpy 2.5.2, macOS 26.6.1
  (arm64)

The byte-reproducibility claims for the tables in data/ hold for exactly
this pinned combination (CI pins colour-science 0.4.7 and numpy 2.5.2);
whether other versions reproduce the bytes has not been tested. Metric
agreement at the documented tolerances is not expected to be
version-sensitive, but the byte-level claim is made only for the pinned
environment.

## The test SPD is never interpolated (§3.5)

§3.5 requires linear interpolation where interpolation is needed and states
that the test source SPD is never interpolated or extrapolated. PyTM30
resamples the CES reflectances and CMFs onto the test SPD's grid and leaves
the test SPD untouched. luxpy cubic-interpolates the test SPD by default.

## Range and increment enforcement (§3.5)

Construction of an SPD enforces §3.5's data rules: samples outside the
380-780 nm calculation range are dropped; an SPD covering less than
380-780 nm (but at least the 400-700 nm minimum) is zero-filled outward to
the calculation range; a wavelength step exceeding 5 nm is rejected with an
error naming the offending gap. The wavelength grid used for the zero-fill
(extending outward at the input's native edge step, final point clamped to
exactly 380/780 nm) is an implementation choice; the standard prescribes
the zeros but not their grid alignment.

## Resampling once per grid is spec-neutral (§3.5)

PyTM30 resamples the CES/CMF/daylight-basis tables to a grid once and
caches them, instead of re-interpolating per SPD as luxpy and
colour-science do. §3.5 governs what is interpolated and how, not how
often. Identical results, a fraction of the work.

## Reference blend Y-normalisation uses the 1964 10-degree observer (§3.1, §3.3)

§3.1 requires the 10-degree observer for all calculations except CCT
determination. The 4000-5000 K reference blend's Y-normalisation
(§3.3) therefore uses the 10-degree y-bar in PyTM30. colour-science uses
the 2-degree observer for this normalisation.

## CCT and Duv: Ohno (2014) as published (§3.3)

§3.3 prints no CCT algorithm; it incorporates one by normative reference
(Ohno, doi:10.1080/15502724.2014.839020). Per §3.1, CCT determination uses
the CIE 1931 2-degree observer. PyTM30 implements the published method: a
LUT search with the triangular solution below |Duv| = 0.002 and the
parabolic solution above. Three deliberate choices:

- **No shifted-triangular blend by default.** The calculators supplied
  with TM-30 and CQS blend the triangular and parabolic solutions below
  the threshold; that refinement is absent from the published method.
  PyTM30 defaults to the published selection rule and exposes the blend as
  an opt-in flag (`CctOptions::shifted_triangular_blend`).
- **No `f_corr` correction factor.** Ohno (2014) publishes a constant
  multiplicative correction for the triangular solution's chord
  approximation, fitted to the paper's 1%-step LUT. The bias it corrects
  shrinks with the square of the LUT spacing; applied to PyTM30's
  0.25%-step LUT it would overcorrect roughly sixteenfold and worsen
  accuracy, so it is omitted. Smet et al. 2023
  (doi:10.1080/15502724.2023.2248397) bound the uncorrected method's
  maximum CCT error at ~0.4 K for a 0.25% LUT.
- **LUT input range.** The Planckian LUT is generated by integrating over
  the CMF's full tabulated range (360-830 nm; see
  tools/generate_planckian_lut.py), describing ideal Planckian radiators.
  The pipeline's CCT path integrates the test SPD over the §3.5
  calculation range (380-780 nm). The two ranges serve different objects
  and are intentionally different.

## Rcs,hj is a percentage; Rhs,hj is a ratio (§4.6, §4.7)

§4.6 computes the local chroma shift as a ratio (Eq. (62)) and requires
percentage representation; §4.7 defines the local hue shift as a ratio
(Eq. (63)) with no percentage requirement. PyTM30 applies the x100 exactly
once, in the core library (`Rcs_hj_percent`), and keeps Rhs,hj a ratio.
colour-science's tm3018 module applies exactly the same asymmetry; luxpy
keeps both quantities as raw ratios.

## Colour Vector Graphic coordinates (§4.5)

Eqs. (58)-(59) place each hue bin's reference position on the unit circle
at the arithmetic mean of the individual CES reference hue angles in the
bin (each sample weighted equally); Eqs. (60)-(61) offset the test position
by the bin-averaged coordinate difference divided by the reference bin
chroma. PyTM30 implements exactly this: unit circle (no display scaling)
and mean-of-individual-hue-angles. luxpy scales its CVG coordinates by a
display factor (default 100) and derives the reference angle from the
bin-averaged coordinates, which weights samples by chroma. PyTM30
additionally carries the bin-average J' alongside the (x, y) coordinates
as a convenience; §4.5 is strictly two-dimensional.

## Local colour fidelity vs local shifts (§4.8, §4.6, §4.7) — conformance note

§4.8 bases local colour fidelity on the individual colour shifts of the
CES within each bin (Eq. (64) averages individual Delta E' values,
lightness included), expressly contrasted with the local chroma and hue
shifts, which use the bin-averaged coordinates. PyTM30 honours the split:
DE_hj/Rf,hj average individual per-sample values; Rcs,hj/Rhs,hj project
the bin-averaged coordinate difference.

## Quadrature

The standard prints its tristimulus formulas as true integrals (§3.6
Eqs. (21)-(28)). PyTM30 evaluates them by the trapezoidal rule, a
quadrature choice the standard leaves open.

## Rf,skin is a research extension (§4.0)

Rf,skin (the mean of the CES15 and CES18 fidelity values) is informed by
§4.2 but is not a standardised TM-30 measure; §1.2 and §4.0 delimit the
standard's own measures. It is labelled as a PyTM30 research extension
everywhere it appears.

## Validity bounds are PyTM30's, not the standard's (§2.0)

The advisory validity flags (CCT within 1000-25000 K, |Duv| <= 0.05)
implement §2.0's qualitative scope statement. The standard prints no
numerical CCT or Duv bounds; the numbers are PyTM30 sanity bounds and are
documented as such at their definition sites.

## Apparent errata in the standard

Two apparent typos in TM-30-20 (not corrected by Errata 1), and the
readings PyTM30 adopts:

1. **Eqs. (60)-(61) mix subscripts in their denominators** (the a' term
   uses the test coordinate where the b' term uses the reference). PyTM30
   normalises both by the reference bin chroma: §4.5 describes the bin
   colour difference as transferred to a position along the *reference*
   circle, and §4.6/§4.7 describe Rcs,hj and Rhs,hj as the radial and
   tangential components of the same vector, which only holds if
   Eqs. (60)-(61) share Eqs. (62)-(63)'s denominator.
2. **§4.3 cross-references "Eq. 3.7.17", which does not exist** (§3.7.1's
   equations are numbered (29)-(51); the hue angle is Eq. (45)). No
   substantive consequence: a' = M' cos(h pi/180) and b' = M' sin(h pi/180)
   with M' > 0, so atan2(b', a') recovers h exactly, and PyTM30's atan2
   route for bin assignment is equivalent to the intended reference.

## What the golden fixtures validate

The fixtures under tests/fixtures/ are produced by
tools/generate_fixtures.py. Three provenance classes, stated explicitly so
that "validated against colour-science" is claimed only where it holds:

- **Independently validated via colour-science primitives:** tristimulus
  integration (`sd_to_XYZ`/`msds_to_XYZ`), CIECAM02, CAM02-UCS, per-sample
  Delta E', Rf, Rf,CESi, Rf,hj (`delta_E_to_R_f`), and Rg's polygon areas
  (`averages_area`).
- **Independent from-spec re-derivation (not colour-science output):** the
  reference illuminant's spectral reconstruction (§3.3 with §3.5's linear
  interpolation of the daylight basis -- colour-science's own D-series
  generator uses Sprague interpolation for those datasets, which §3.5 does
  not permit here), the CVG coordinates (§4.5), and the Rcs,hj/Rhs,hj
  projections (§4.6/§4.7). These are computed in the generator from the
  cited equations, independently of the C++ code.
- **Same-algorithm port (self-consistency, not independent validation):**
  the CCT/Duv LUT search. The generator runs the same published Ohno
  (2014) method against the same LUT the C++ engine uses; an earlier
  generator revision using colour-science's independent Ohno solver agreed
  to within ~0.06 K but injected enough reference-illuminant noise to
  obscure the tighter fixture tolerances (see the docstring in
  tools/generate_fixtures.py).
